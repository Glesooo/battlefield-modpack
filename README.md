# Battlefield — система обновлений (Packwiz)

Вместо заливки всей сборки на Google Диск при каждой правке: здесь лежит **манифест** (какие
файлы должны быть у игрока и с какими хэшами), сами моды хранятся как ассеты одного GitHub
Release, а игрок один раз кладёт `update.bat` в свою папку `minecraft` и дальше просто
запускает его — скачивается только то, что реально изменилось.

Инструмент — [packwiz](https://packwiz.infra.link/), готовый и хорошо проверенный, писать
свой протокол синхронизации не понадобилось.

## Как это устроено

- `pack.toml` / `index.toml` — манифест packwiz, реген через `packwiz refresh`.
- `mods/*.toml` — по одному файлу на мод (~90 штук, ~0.48 ГБ). Сам jar НЕ лежит в git — только
  имя, хэш и прямая ссылка на GitHub Release с ассетами (тег `mod-files`).
- `tacz/` — тут ДВЕ разные вещи в одной папке, это осознанно (у ганпаков-zip и мелких файлов
  рядом с ними общий целевой путь на компьютере игрока — `<инстанс>/tacz/`):
  - **`tacz/*.toml`** — большие zip-ганпаки (~0.5 ГБ) — тем же способом, что моды: сам zip
    только на GitHub Release, здесь — указатель.
  - **Остальное в `tacz/`** (несколько мелких распакованных подпапок вроде `daffas/`,
    `endlessammo/` — похоже, их сами создают некоторые ганпак-моды при первом запуске — плюс
    пара служебных файлов) — обычные файлы прямо в git, как конфиги ниже.
  - `publish.ps1` не путает эти два вида между собой (раздельная логика очистки/копирования),
    но если руками полезешь в эту папку — не трогай `.toml`, это чужая зона.
- `config/` — копия **только** общей клиентской `PrismLauncher/instances/M.A.C.E/minecraft/config/`
  (~1.4 МБ, обычные файлы прямо в git). Раз решили затирать конфиги под твою версию — так оно и
  работает: у packwiz это поведение по умолчанию для любого отслеживаемого файла, никакого
  спецфлага не нужно.
- **Специально НЕ трогается:** `saves/` целиком (это мир игрока, не часть сборки) и, отдельно,
  `saves/<мир>/serverconfig/` — в Forge 1.20.1 серверные конфиги (`FactionConfig`,
  `DeathmatchConfig` и т.п.) хранятся **внутри сохранения мира**, а не в общей папке. Это данные
  конкретного игрока/мира — апдейтер их не видит и не трогает.

Суммарно на момент настройки — mods (~0.48 ГБ) + tacz (~0.5 ГБ) + config (~1.4 МБ) ≈ 1 ГБ.
Если реальный вес сборки у тебя больше (упоминал ~1.7 ГБ) — вероятно, за счёт `saves/` (мир
весит немало) или ресурспаков/шейдеров, которых на момент настройки не было; если появятся
`resourcepacks/`/`shaderpacks/` с содержимым — скажи, добавлю их в `publish.ps1` той же схемой
(бинарники крупнее нескольких МБ — через Release, мелочь — как конфиги).

## Разовая настройка (сделать один раз)

1. **Авторизовать GitHub CLI** (под своим аккаунтом, я не могу сделать это за тебя):
   ```powershell
   gh auth login
   ```
   Выбрать GitHub.com → HTTPS → войти через браузер.

2. **Создать приватный репозиторий** (например `battlefield-modpack`):
   ```powershell
   gh repo create battlefield-modpack --private --source=. --remote=origin
   ```
   Выполнять из папки `ModpackDist` (эта). `--private` — важно, часть модов сторонняя
   (некоторые с лицензией All Rights Reserved), репозиторий не для публичного доступа, только
   для тех, кому даёшь доступ (`gh repo add-collaborator` или просто добавить друзей в Settings
   → Collaborators на GitHub, либо сделать репозиторий доступным по прямой ссылке — приватные
   репозитории всё равно требуют, чтобы приглашённый принял приглашение и был залогинен, так
   что для игроков, не имеющих GitHub, `raw.githubusercontent.com`-ссылки на приватный репо
   **не откроются** без токена — см. примечание ниже).

   **Примечание про приватность и игроков без GitHub-аккаунта:** если played не должны
   регистрироваться на GitHub, репозиторий с манифестом придётся сделать публичным (сам
   `pack.toml`/`index.toml`/конфиги — не секрет), а вот Release с самими модами можно
   оставить в том же паблик-репо (то же самое разграничение смысла не имеет технически: раз
   репо публичный, публичны и релизы). Если стороннние ARR-моды пугают публичным репо —
   вариант: приватный репозиторий + `gh` личный токен с правом `repo`, вписанный в URL, что
   игроку тоже придётся один раз настроить. Если группа маленькая и все свои — проще всего
   сделать репозиторий **публичным** (не более "публично", чем сейчас Google Диск с ссылкой
   которую можно переслать кому угодно) и не усложнять токенами. Выбор оставляю тебе.

3. **Первая публикация** (загрузит все ~87 модов и конфиги, минут 5-10 в зависимости от
   скорости интернета):
   ```powershell
   .\publish.ps1 -Repo "Gleso/battlefield-modpack"
   ```
   Для 87 разнообразных сторонних jar'ов **стоит проверить `git status`/лог перед вторым
   запуском**, если что-то показалось не так - это первый прогон скрипта на таком объёме
   реальных файлов, а не сотня протестированных руками случаев.

4. **Прописать ссылку в `update.bat`** — заменить `OWNER/REPO` в строке `PACK_URL` на
   `Gleso/battlefield-modpack` (или как назвал репозиторий), закоммитить и запушить (это тоже
   входит в `publish.ps1`, если файл лежит в этой же папке — просто не забыть поправить перед
   первым `publish.ps1`).

## Как публиковать обновления дальше

Просто:
```powershell
.\publish.ps1 -Repo "Gleso/battlefield-modpack"
```
Скрипт сам найдёт, какие jar'ы в `mods/` M.A.C.E добавились/изменились/пропали, перезальёт
только их, скопирует текущий `config/`, обновит манифест и запушит. Если менял только один
мод (например, пересобрал `HudElements`) — перезальётся только он, остальное не тронется.

## Что нужно сделать игроку (один раз)

1. Скачать `update.bat` (и, если сборка новая, ничего больше — `packwiz-installer-bootstrap.jar`
   скачается сам при первом запуске).
2. Положить `update.bat` прямо в `PrismLauncher\instances\<Имя инстанса>\minecraft\`.
3. Запускать его каждый раз, когда сказано, что вышло обновление.

Первый запуск скачает всю сборку (раз ничего ещё не установлено) — так же долго, как раньше
через Диск. Дальше — только разницу.
